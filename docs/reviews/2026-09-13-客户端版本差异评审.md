# Prelay Client 版本差异评审报告

## 评审范围

本次评审 `prelay-client` 两部分改动：

## 评审依据

## 总体结论

三天的改动集中在两件事：MCP 扩展安装（模块拆分、Codex / OpenCode 配置写入、状态文件、安装抽屉）与「Skill 与规则安装状态 + 移除 Claude Code 客户端」。拆分后的 `src-tauri/src/extensions` 职责清楚（`mod.rs` 从 211 行降到 19 行，拆成 `model`、`catalog`、`install`、`mcp`、`mcp_manifest`、`rules`、`skills`、`support`），状态模型（按宿主在 `.prelay/` 下记录包名、版本、commit 与清单快照）与设计文档一致，MCP 与 Codex/ChatGPT 共用一套配置也符合既有集成定义（`integrations/chatgpt.rs:22-28`）。

但当前 HEAD 不能直接发布：**release 门禁的 `lint` 与 `format:check` 在本机复现失败**；另有 MCP 状态计算漏掉 ChatGPT、供应商 Anthropic 协议收窄与服务端不一致等问题；工作树里的两类未提交改动需要先提交，否则会出现「文档已声明移除、代码仍然带着联调入口」的不一致。

## 主要问题

### 当前 HEAD 未通过 release 门禁的 lint 与格式检查（阻断）

`bun run lint` 报错：

```text
app\components\extensions\ExtensionInstallationScope.vue
  5:7  error  'props' is assigned a value but never used  @typescript-eslint/no-unused-vars
```

`bun run format:check` 报错（真实问题两项）：

- `app/components/agents/AgentClientAvatarGroup.vue`：`.filter((definition): definition is ... =>` 的参数换行需要按 prettier 重排；
- `app/components/extensions/ExtensionInstallationScope.vue`：`</script>` 前多一个空行。

`ExtensionInstallationScope.vue` 是在 `8b2b547`（2026-09-11）之后新增的文件，`AgentClientAvatarGroup.vue` 新增于 `0577d5e`，两者都晚于 `v0.1.12`，因此从未经过 verify 门禁。`release.yml` 在 `verify` 阶段会依次执行 typecheck、lint、format:check、测试和 Rust 检查，打 tag 会在 lint 处失败。修复成本极低，建议在提交工作树改动前先补齐。

### MCP 状态计算漏掉 ChatGPT（重要）

`src-tauri/src/extensions/catalog.rs:166-172` 的 `mcp_agent_clients` 在计算 MCP 列表状态前把 `ChatGpt` 过滤掉，只保留 `CodexCli` 与 `OpenCode`；而 `src-tauri/src/extensions/mcp.rs:29-34` 明确把 `ChatGpt` 映射到 Codex 宿主，设计文档 `docs/superpowers/specs/2026-09-12-mcp-extension-installation-design.md:55` 也要求“状态计算时同一份记录可以同时代表两个客户端”，并在验收标准中列出“只检测到 ChatGPT 时，安装仍然写入 Codex 配置”。

后果：只检测到 ChatGPT 的机器（设计文档明确支持的场景）在 MCP 分类下永远看到“安装”，`installedClients` 为空，安装完成后状态也不变；`mcp::retain_listed_mcp_packages` 同样因为客户端列表为空而不清理状态记录。

由于 `mcp_hosts` 本身用 `BTreeSet` 按宿主去重，这个过滤并不必要；保留 `ChatGpt` 即可同时修正安装、状态与清理三条路径。

### 供应商协议的 Anthropic 收窄与服务端现状不一致（重要）

提交 `a0197bb`（“移除 Claude 客户端接入”）在客户端删除了 Anthropic 协议表达：

- `app/stores/relay.ts:9` 的 `UpstreamProtocol` 不再包含 `anthropic`；
- `app/utils/providerTemplates.ts:104` 把 `anthropic_messages` 映射为 `null`；
- `protocolLabel` / `protocolTagPalette` 不再识别该协议（`tests/provider-capabilities.test.ts:95` 断言返回 `-`）。

而服务端仍然保留：`config/catalog/providers.toml` 中 deepseek 与 kimi 的 `protocols` 与 `protocol_base_urls.anthropic_messages`、`/v1/messages` 入口，以及请求记录里的 `protocol_in = "anthropic_messages"`（`prelay-server/src/routes/v1/messages/*.rs`）。

由此产生两处可见影响：

- 活动列表：`app/components/activity/RequestTable.vue:186-189` 用 `protocolLabel(row.protocol_in)` 渲染协议列，所有 Anthropic Messages 请求现在显示为 `-` 与灰色。
- 供应商编辑：`app/composables/useProviderForm.ts:173-178` 按客户端协议集合重建 `protocolBaseUrls`，保存时 `267-275` 又用同一集合重写 `protocol_base_urls`；服务端 `prelay-server/src/storage/providers.rs:256-261` 是整体替换 capabilities。因此编辑一个既有 deepseek/kimi 供应商会**静默删除** `protocol_base_urls.anthropic_messages` 并把 `supported_protocols` 收窄，`/v1/messages` 从原生 Anthropic 上游退化为 chat_completions 桥接；从目录模板新建供应商也会丢掉同样的信息。

提交信息写的是“保留服务端协议边界”，与上述行为冲突。需要确认这是有意的能力收窄（则服务端目录、`/v1/messages` 与活动展示应一起下线），还是客户端应保留映射、只移除 Claude Code 客户端接入。

### HEAD 处于「文档已写、代码未提交」的中间态（重要）

设计文档 `docs/superpowers/specs/2026-09-12-mcp-extension-installation-design.md:349` 已声明联调入口“已删除”，但 HEAD 上仍然存在：

- `src-tauri/src/commands/extensions.rs:31` 的 `extensions_mcp_test_package` 命令与 `src-tauri/src/app/mod.rs` 的注册；
- `src-tauri/src/extensions/local.rs` 的本地模拟清单（`local://mcp-test`，20 个环境变量引用）；
- `app/pages/agents.vue` 的“安装”临时按钮与 `AgentWorkspaceContent.vue` 的 `install-test` 事件；
- `src-tauri/tests/command_registration.rs` 中对应的夹具测试。

这组清理正好在工作树里（已删除 `local.rs`、命令、注册、按钮与测试），尚未提交。若从当前 HEAD 打 tag，会带着联调入口和一个“本地测试 MCP”包发布，因此工作树改动需要在发布前提交。

### 环境变量输入值被丢弃且界面没有说明（重要）

设计文档 `:205` 与 `:353` 说明：环境变量取值只存在于界面状态，安装请求只携带扩展包、目标客户端和覆盖标记，不写入宿主配置，也不进入本地状态。实现与之一致（`ExtensionInstallRequest` 无取值字段）。

但 `app/components/extensions/McpInstallForm.vue:88-101` 仍然为每个变量渲染密码输入框，抽屉里没有任何“本机环境变量、不会保存”的提示。用户输入密钥后点击安装会成功，但取值既未被保存也未被使用；下一次打开抽屉取值已被清空（`ExtensionInstallDrawer.vue:174`）。建议改为说明型展示，或明确提示需要用户自行在本机环境变量中提供，避免让用户以为密钥已被保存。

## 次要问题

### `enabled` 与“停用由用户自行处理”的说明矛盾

设计文档 `:285` 写“用户需要停用 MCP 时，在对应智能体的 MCP 配置中处理”，但状态判断包含 `enabled`：`mcp_server_table` 写入 `enabled`（`src-tauri/src/agents/integrations/codex_cli.rs:146`），`mcp_server_matches`（同文件 `64-86`）与 `mcp_installation_status`（`extensions/mcp.rs:175-183`）按整表比较。用户把 `enabled` 改成 `false` 后，扩展会长期显示“更新”，再次安装又会把它改回 `true`。建议比较时忽略 `enabled`，或修正文档。

### Skill 状态不校验目录是否仍然存在

`extensions/skills.rs:196-234` 只用 `skill.json` 判断“安装 / 更新 / 补装 / 已安装”，不检查 `<root>/<skill>` 目录是否存在；MCP 路径有 `mcp_server_exists` 校验（`extensions/mcp.rs:165-170`）。用户手工删除技能目录后，列表会一直显示“已安装”。

### 旧状态迁移发生在读取路径且无并发保护

`extensions/skills.rs:151-172` 的 `read_installed_skill_packages` 在新状态文件缺失时调用 `migrate_legacy_skill_packages`，后者写入新状态后立即 `fs::remove_dir_all(旧目录)`（`skills.rs:335-336`）。读取操作产生写入与删除副作用，且没有互斥：扩展列表与智能体条目可以并发刷新（`app/composables/useExtensionUpdates.ts:16`、`:33` 使用 `Promise.all`），并发迁移时后到的删除会拿到 `NotFound` 并向上报错。建议把迁移拆成显式入口，或对删除旧目录做容错。

### 同一校验规则在两个仓库各写一份

客户端的 `src-tauri/src/extensions/mcp_manifest.rs:21-133` 与服务端 `prelay-server/src/extensions/mcp.rs` 的 `validate_mcp_manifest` 逐条等价（保留服务名、`cwd`、`enabled`、明文凭据、URL 结构、环境变量同名引用），差异只在错误粒度（客户端分 stdio / HTTP 两类消息，服务端统一为 `ContentInvalid`）。同一契约的两份实现容易漂移，建议下沉到 `prelay-protocol`（例如 `ExtensionMcpManifest::validate()`）或至少增加跨仓一致性用例。

### MCP 安装的局部失败与空选择

- `extensions/mcp.rs:125-143` 先删除旧服务名配置再写入新配置：若 `upsert_mcp_server` 因宿主配置解析失败而中断，旧配置已删、状态文件未更新，用户原有的服务配置会丢失（下一次列表会因 `mcp_server_exists` 为假而清掉状态记录，最终可恢复为“安装”）。可考虑先写入后删除，或先落状态再改配置。
- `extensions/mcp.rs:89-123` 在客户端列表为空时不会报错，`install_extension` 仍返回“已安装 X。”。界面已禁止空选择（`ExtensionInstallDrawer.vue:282`），但命令层建议显式拒绝空目标。

### 未提交的 Agent 设置改动需要单独说明

工作树中的 `disable_response_storage` 清理（`src-tauri/src/agents/settings/codex.rs:38` 显式删除键、`settings/mod.rs` 去掉字段）方向清楚，与“已不被当前 Codex 版本识别”的注释一致。同批新增的 `ensure_table_bool` 默认值与 `[desktop] enabled-reasoning-efforts` 硬编码列表（`codex.rs:102-121`，含 `ultra`、`persistent`、`max`）把 Codex 特性开关与思考档位固定在客户端代码中，且不与目录里的 `reasoning_efforts` 做一致性校验；这些值只能在真实 Codex 版本上验证，本轮未验证。提交时建议把「联调入口清理」与「设置字段清理」分成两个逻辑提交。

- `package.json` 与 `src-tauri/Cargo.toml` 的版本仍是 `0.1.12`，发布流程尚未启动；本轮结论针对工作树状态，提交与发布后需要按提交后的 tree 复验门禁。
