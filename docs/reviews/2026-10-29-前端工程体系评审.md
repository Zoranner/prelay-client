# Prelay Client 前端工程评审报告

## 评审范围

本次只评审 `prelay-client` 的 Nuxt/Vue 前端工程体系、目录边界、命名、依赖治理、测试与验证、仓库产物，不评价功能需求完成度、视觉喜好或单个交互缺陷。

## 评审依据

- `review-engineering` 通用工程基线和 `stacks/nuxt.md` 专项清单。
- `prelay-client/AGENTS.md` 中的前后端边界、UI 约定和验证要求。
- `package.json`、`nuxt.config.ts`、`eslint.config.mjs`、`prettier.config.mjs`、`.editorconfig`、`.gitignore`、`.gitattributes`。
- `.github/workflows/release.yml`、`README.md`、当前源码、测试和 Git 工作区状态。
- 用户确认：公司内网私有源是构建前提，`.npmrc` 和发布流程中删除 `bun.lock` 后安装是既定方式。

## 总体结论

目录重构后的主干结构已经清楚：页面负责组合，业务组件按 `agents`、`extensions`、`providers`、`endpoints`、`dashboard` 等领域分层；`components`、`utils`、`composables` 中已经没有单文件包装目录；按 `~/` 静态导入关系扫描 91 个 `app` 源文件，未发现导入环路。

当前主要风险不在目录是否足够深，而在工程边界是否真正稳定：

- 客户端 chunk 警告已消除，Nitro external 警告仍在。
- 测试大量读取源码文本，重构路径或调整模板会触发成批测试修改。
- Providers 页面仍承担多个独立工作流。
- `utils/model/endpoints.ts` 仍读取目录 store，作为领域适配保留。

`.npmrc` 指向内网源、发布流程删除锁文件后安装，属于已确认的环境约束，不按工程缺陷处理；外部网络环境无法直接复现时需要明确说明前置条件。

- `prelay-client/.npmrc` 指向公司内网 `@stellar` 源，是当前依赖安装的必要配置。
- `.github/workflows/release.yml` 在安装前删除 `bun.lock`，是内网源条件下的既定发布流程。
- 上述两项不作为问题或整改项；评审只记录风险边界：外部 CI、未接入内网的新开发者需要先具备公司内网访问和源认证条件。

## 主要问题

以下为评审时记录的问题和证据；本轮已经处理的项目，处理状态见文末“整改进展”。

### 构建警告未清零

**定性：违反硬性工程基线。**

证据：

- `bun run generate` 成功，但最大 chunk 为 `1,125.16 kB`。
- Nitro 输出 `cache-driver.mjs` unresolved external 警告。
- Nitro 输出 `h3` 未使用 external 导入警告。

风险：

- 大 chunk 会放大桌面端首屏加载和内存压力，也会掩盖后续体积回归。
- Nitro external 警告会降低构建日志可信度，真实问题容易被噪声淹没。

建议：

- 先做一次 bundle 组成分析，确认大 chunk 是否来自 ECharts、`@stellar/ui`、Tauri API 或重复依赖。
- 对图表和重型面板保持动态导入，按页面或功能拆分 vendor chunk。
- 核对 Nuxt/Nitro 版本组合，确认 `cache-driver.mjs` 和 `h3` 警告是否属于当前版本的框架内部问题；如果是，记录版本依据，不要用提高告警阈值代替处理。

### 测试体系与源码文本强耦合

**定性：规范缺失导致风险。**

证据：

- 38 个测试文件中有 27 个使用 `readFileSync` 读取源码。
- 多个测试直接断言模板片段、导入路径和字符串常量，例如 `tests/provider-flow.test.ts` 439 行、`tests/endpoint-models.test.ts` 377 行、`tests/extensions-flow.test.ts` 330 行、`tests/app-shell.test.ts` 330 行。
- 本次目录重命名需要同步修改大量测试路径，说明测试没有稳定在行为契约上。

风险：

- 文件重命名、组件拆分或模板调整会产生大量非行为性失败。
- 测试给了“覆盖很多”的错觉，但无法证明运行时行为。
- 结构门禁和业务行为测试混在一起，后续维护者难以判断失败原因。

建议：

- 只保留一个轻量的 `source-layout.test.ts` 负责目录和命名门禁。
- 行为测试优先导入纯函数、composable 或组件契约，减少对源码文本的 `toContain`。
- 对必须保留的结构断言，集中到结构门禁，不散落在各业务 flow 测试中。

### `stores/relay.ts` 混合 DTO 类型和 store 状态，`utils` 反向依赖 stores

**定性：建议优化。**

证据：

- `app/stores/relay.ts` 共 422 行，包含 55 个 `export interface`/`export type`，真正的 `useRelayStore` 从第 407 行才开始。
- `app/utils/agent/*`、`app/utils/model/*`、`app/utils/provider/*` 多处直接从 `~/stores/relay` 导入 DTO 类型。

风险：

- 传输 DTO、前端视图类型和 store 状态混在同一文件，协议变更会持续推高单文件体积。
- 纯工具层依赖 stores 类型，目录边界表达的是“工具依赖状态层”，而不是“工具依赖共享类型”。
- 新类型很容易继续堆进 `relay.ts`，形成新的类型集散地。

建议：

- 将共享 DTO 和视图类型移到 `app/types/`，按协议、Provider、Endpoint、Agent、Extension 两到三个有共同变化的模块组织，不必逐类型拆文件。
- `stores/relay.ts` 只保留 bootstrap 等真正的状态所有权。
- `utils` 只依赖类型模块，不依赖 store 实现。

### `utils/model/catalog.ts` 内含响应式单例和 `useModelCatalog`

**定性：建议优化。**

证据：

- `app/utils/model/catalog.ts:15-17` 定义模块级 `shallowRef` 和 `ref` 状态。
- 同文件 `:75` 导出 `useModelCatalog`。
- `providerForm.ts`、`agent/settings.ts`、`agent/sync.ts` 都把它当作全局目录状态使用。

风险：

- `utils` 不再是纯工具层，目录名与实际职责不一致。
- 模块级响应式状态难以显式重置和隔离，测试容易受执行顺序影响。
- `use` 函数放在 `utils` 而不是 `composables`，会绕过当前组合式目录约定。

建议：

- 将目录的响应式状态和 `useModelCatalog` 移到 `app/composables/modelCatalog.ts` 或独立 store。
- `utils/model/` 只保留纯查询、索引和格式化函数。

### 工作区布局只共享 CSS，不共享组件契约

**定性：建议优化。**

证据：

- `app/components/agents/workspace/Content.vue` 和 `app/components/extensions/library/Content.vue` 都使用 `workspace-main`、`workspace-toolbar`、`workspace-results`。
- 两个组件分别通过 `<style scoped src="../../shell/layout/workspace.css">` 引入同一份样式。
- 两个组件的结构、工具栏和结果区布局各自复制。

风险：

- 样式已经共享，但 DOM 结构和插槽契约没有共享，改布局需要同时修改两个领域组件。
- `shell/layout` 既放基础布局组件，又放跨领域工作区样式，边界不够明确。

建议：

- 如果两个工作区继续共享布局，提取一个带 `toolbar`、`default` 插槽的 `WorkspaceLayout.vue`，让两个领域组件只提供内容。
- 如果两者后续会独立演化，则各自拥有自己的样式，不保留跨领域 CSS 引用。

### 未使用的 Dashboard 组件

**定性：建议优化。**

证据：

- 40 个非页面组件中，只有 `app/components/dashboard/charts/Heatmap.vue` 和 `app/components/dashboard/charts/RequestOutcome.vue` 没有被 `app` 中的显式导入引用。
- `Heatmap.vue` 仍有对应测试，但页面没有挂载；`RequestOutcome.vue` 没有页面或测试引用。

风险：

- 死代码会继续被维护、格式化和测试，增加误导。
- 测试会保护一个并不存在的用户路径，降低测试信号价值。

建议：

- 如果后续确实要展示活跃度和请求结果，接入页面并补运行时验证。
- 如果不计划使用，删除组件及对应测试和样式，避免把“未接线”当成已完成能力。

### Providers 页面仍承担多个独立工作流

**定性：建议优化。**

证据：

- `app/pages/providers.vue` 共 384 行，负责列表加载、目录加载、连通性 Ping、保存、删除、编辑抽屉、共享抽屉和退出守卫。
- `app/composables/providerForm.ts` 375 行、`app/components/providers/Form.vue` 356 行，表单本身已经独立。

风险：

- 列表、CRUD、Ping、共享是独立变化的工作流，却集中在同一个页面控制器里。
- 异步状态、错误处理和抽屉生命周期继续增加时，页面会重新变成编排与业务混合层。

建议：

- 只在职责确实独立时抽取 `useProviderSharing`、`useProviderList` 或 `useProviderOperations`，不要为了行数机械拆分。
- 让页面保留组合和抽屉开关，把命令调用、共享状态加载和列表刷新分别归位。

### 根目录过程产物和文档门禁漂移

**定性：建议优化。**

证据：

- `whole-fix-report.md` 已被 Git 跟踪，但报告中的 Bun 结果是 147 passed，当前为 217 passed，属于过期过程报告。
- 根目录存在未跟踪文件 `$null`，内容是一段 Git 参数错误信息。
- `README.md:21-22` 和 `AGENTS.md:31-32` 只列出 `bun test`、`bun run typecheck`，而 `release.yml:54-58` 和 `tests/quality-gate.test.ts` 还要求 `bun run lint`、`bun run format:check`。

风险：

- 根目录过程报告和临时文件会污染仓库，过期结论会误导后续维护。
- 文档中的验证入口少于真实门禁，开发者可能漏跑 lint 和格式检查。

建议：

- 删除根目录 `$null`，将需要保留的报告放到 `docs/reviews/`，过程性报告不进入仓库。
- 更新 README 和 AGENTS 的验证命令，明确 lint、format check、typecheck、test、generate 的适用顺序。

### 自动导入范围偏宽

**定性：建议优化。**

证据：

- `nuxt.config.ts:25-26` 配置了 `["composables/**", "utils/**"]`。
- 当前 `app/utils` 的使用方基本都显式导入，`utils/**` 的全局扫描会扩大隐式命名空间。

风险：

- 工具函数可能在未来出现同名或隐式依赖，降低依赖可追踪性。
- 真正的缺失导入可能被自动导入掩盖。

建议：

- 保留 `composables/**` 以支持嵌套组合式函数的自动导入。
- 如果确认所有 utils 都显式导入，移除 `utils/**`，让工具依赖保持可搜索和可审计。

## 整改进展

本轮已经处理：

- 将 `stores/relay.ts` 的 DTO 类型移入 `app/types/relay.ts`，store 只保留 bootstrap 状态。
- 将模型目录状态和 `useModelCatalog` 移入 `app/stores/modelCatalog.ts`，`providerModelOptions` 一并归位。
- 用 `WorkspaceLayout.vue` 统一智能体和扩展库的工作区结构，删除独立 `workspace.css`。
- 将 Providers 分享加载、保存和抽屉状态抽到 `app/composables/providerSharing.ts`，页面只保留列表、Ping 和 CRUD 编排。
- 删除未使用的 `Heatmap.vue`、`RequestOutcome.vue` 及失效测试。
- 将 ECharts 从完整入口改为 core 按需注册，并拆分 chart 注册模块；最大客户端 chunk 从 1,125.16 kB 降至 329.80 kB。
- 删除根目录 `$null` 和过期 `whole-fix-report.md`，补充 README/AGENTS 的内网源和验证命令说明。
- 移除 `utils/**` 自动导入，工具依赖改为显式导入。

仍需处理：

- Nitro 的 `cache-driver.mjs` 和 `h3` external 警告是 Nitro 2 的已知问题，官方在 Nuxt 5/Nitro 3 中处理（[nuxt/nuxt#36278](https://github.com/nuxt/nuxt/issues/36278)）；当前 Nuxt 4.5.2 组合不升级主版本时只能记录边界。
- 业务 flow 测试仍有大量源码字符串断言，尚未迁移为行为测试。
- `app/pages/providers.vue` 仍集中承担列表、Ping、CRUD 和退出守卫，分享已移出。

## 整改优先级建议

### 先处理构建门禁和环境说明

- 保留 `.npmrc` 和现有内网发布流程，在 README 或交付说明中明确内网源、认证和锁文件删除流程的适用边界。
- 分析并拆分超过 500 kB 的客户端 chunk，确认 Nitro external 警告的来源。

### 再处理边界和测试信号

- 将共享 DTO 类型从 `stores/relay.ts` 分离到 `app/types/`，保留 store 只管理状态。
- 将 `useModelCatalog` 和目录响应式状态移出 `utils`。
- 减少业务测试对源码文本的依赖，保留集中式结构门禁。
- 视实际变化压力抽取 `WorkspaceLayout.vue` 和 Providers 页面工作流 composable。

### 最后清理噪声

- 删除未使用的 Dashboard 组件或将其接入页面。
- 清理根目录过程产物，更新 README 和 AGENTS 的验证说明。
- 复核 `utils/**` 自动导入是否可以收缩为显式导入。
